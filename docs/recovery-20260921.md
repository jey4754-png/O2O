# 주문 조회 권한 복구 기능

## 배경

주문·상품·그룹의 조회 권한은 브라우저에 보관된 권한 키의 해시로만 판정한다. 전화번호와 visitorId 는 사장님·그룹 화면에 노출되는 값이라 증명으로 인정하지 않는다(`filterCustomerOrdersForProof_` 주석).

모바일 브라우저가 사이트 저장소를 비우면 세 키가 한꺼번에 사라지고, 그 사용자는 내 주문 0건·사장님 관리 0건·그룹 채팅 불가 상태가 된다. 2026-09-17~09-20 고객 보고의 "하루만 지나면 0으로 뜬다"가 이 현상이다.

## 설계 원칙

**전화번호는 조회 범위이지 권한 근거가 아니다.** `publishCustomerOrder_`는 `order.customerPhone`을 클라이언트 값 그대로 받아 길이만 검사한다. 전화번호를 근거로 권한을 주면 남의 번호로 주문 한 건을 만든 뒤 그 번호의 모든 주문과 취소 권한까지 인수할 수 있다.

**시트 행을 다시 쓰지 않는다.** 같은 주문에 소유 해시가 둘이면 `filterCustomerOrdersForProof_`가 충돌로 판정해 원래 주인에게까지 숨긴다. 소유 해시는 주문 내역과 이벤트 로그 스냅샷 양쪽에 있고 스냅샷은 상태 전이마다 누적되므로, 재작성 방식은 부분 실패가 곧 영구 은닉이 된다. 대신 **승계만 기록하고 읽는 시점에 해석한다.**

**확인번호 원문은 Apps Script 에 도달하지 않는다.** scrypt 파생·비교는 Vercel 에서만 한다.

## 고객 자가 등록·복구 (2026-09-22)

`api/recovery.js` 가 사용자 앱과 콜렉터 `recovery_credentials` 사이에 선다. 확인번호는 이 함수 안에서만 scrypt 로 파생·비교되고, 콜렉터에는 검증자(등록)나 맞춘 검증자의 ref(복구)만 간다. 전화번호도 콜렉터에는 `HMAC(콜렉터 토큰, 전화번호)` 식별키로만 간다.

- **등록** (`action: 'enroll'`): 전화번호(010, 11자리) + 확인번호(숫자 6~12자리) + 이 브라우저의 주문 키·그룹 자격·상품 관리키. 콜렉터가 실제 소유가 증명되는 것만 결박하고, 하나도 증명되지 않으면 `recovery_nothing_to_bind` 로 등록하지 않는다. 등록 버킷은 결과와 무관하게 슬롯을 소모한다.
- **복구** (`action: 'redeem'`): 콜렉터가 돌려준 8개 후보(실제+미끼)를 전부 파생해 비교한다. 못 맞추면 `finish` 로 실패를 기록하고 `invalid_recovery_pin`(403). 등록되지 않은 번호도 같은 실패로 보인다. 맞추면 새 키 해시로 승계를 기록하고 `actorId`·`groups`·`deals` 를 돌려준다(옛 해시는 돌려주지 않는다).
- **화면** (`src/App.jsx` 내 주문): 목록이 있으면 "확인번호 등록" 폼이 열린다(등록 뒤에는 새 주문이 생겼을 때만 다시 열림). 조회가 끝났는데 목록이 비면 "확인번호로 되살리기" 폼이 위에 나온다. 되살린 뒤 브라우저는 결박된 그룹에 새 주문 키를 참여자 자격으로 저장하고, 결박된 상품에 같은 키를 관리키로 저장하며(`phone:` 범위), 그룹 자격이 하나도 없던(=비워진) 브라우저만 돌려받은 `actorId` 를 방문자 ID 로 채택한다.

**등록은 그 시점의 스냅샷이다.** 등록 뒤에 넣은 주문은 다시 등록하기 전까지 결박되지 않는다. 화면은 로컬에 등록 시점 주문 수를 남겨 "등록 이후 새 주문 n건" 으로 재등록을 권한다. 서버는 이 수를 모른다.

검증: `tests/recovery-api.test.js`(콜렉터 실제 코드 + API 핸들러, 5건), `tests/e2e/customer-history-ui.spec.js` 되살리기·등록 2건.

**배포 순서.** 웹의 등록·복구 폼은 콜렉터 `recovery_credentials` 를 부른다. 현재 운영 콜렉터(v25)는 이 액션을 모르므로 `invalid_action` → 화면에는 "복구 서버에 연결하지 못했습니다" 가 뜬다. 따라서 **웹은 사장님이 Apps Script 를 `main` 최신으로 배포한 뒤에 올린다.** 그 전에는 현재 운영 웹(`b9e832f`, 관리자 재연결 안내까지)을 유지한다.

## 관리자 재연결 사용법

1. 사용자가 자기 기기의 사용자 앱에서 **복구 코드**를 확인한다. 이 값은 권한 해시(공개 식별자)이며 원본 토큰이 아니다.
2. 관리자가 **대면·유선으로 본인을 확인**한다. 이 전제는 두 화면에 명시되어 있다.
3. 관리자 앱 → 상품·주문 관리 → 해당 상품 → 재연결할 주문 선택 → 복구 코드 입력 → 사유 입력 → 실행.

제약:
- 한 번에 최대 50건, 소유 키가 서로 다르거나 없는 주문은 함께 묶지 않는다.
- 한 기기에 두 번째 승계를 기록해 기존 승계를 무효로 만들 수 없다.
- 권한보다 이력을 먼저 남긴다. 이력 기록이 실패하면 권한도 생기지 않는다.

## 작업 중 발견해 수정한 기존 결함

- `rate_begin`이 호출 버킷과 무관하게 **관리자 PIN 검증자를 응답에 싣고 있었다.** 복구가 같은 리미터를 재사용하면 관리자 자격증명이 복구 응답으로 새어 나간다. 관리자 버킷일 때만 싣도록 막았다.
- 주문 확인 키를 저장하는 곳만 저장공간 부족 복구가 빠져 있어, 저장이 실패하면 다음 접속에 새 키가 만들어지고 이전 주문 전체가 조회 대상에서 빠졌다.

## 자체 검토에서 닫은 반쪽 복구

승계를 조회 경로에만 걸어 두면 방과 상품 목록은 열리는데 그 방의 주문 게시와 그 상품의 수정·삭제만 막히는 **조회 전용 복구**가 된다. 사용자에게는 복구가 된 것처럼 보이고 실제로는 아무것도 못 하는 상태라 더 나쁘다. 두 지점을 닫았다.

- `requireParticipantCapability_` 가 승계를 해석하지 못해 복구한 기기의 그룹 주문 게시가 `invalid_participant_capability` 로 막혔다. 결박 근거(시트·그룹·참여자)를 넘겨 해석하게 했다.
- 상품 게시·삭제가 저장된 사장님 해시와 정확히 같은 값만 통과시켜, 복구한 사장님이 자기 상품을 목록에서 보면서도 고칠 수 없었다.

두 경로 모두 **결박된 것에만** 적용된다. 등록 시점에 증명되지 않은 그룹·상품, 제3자의 키, 등록 이후 정상 경로로 권한 토큰이 교체된 결박은 그대로 거부한다.

승계로 인가된 쓰기는 **저장된 소유 표시를 바꾸지 않는다.** 주문 축에서는 이벤트 로그 스냅샷과 주문 행에 해시가 둘이 되어 그 주문이 양쪽 키에서 영구히 사라지기 때문이고(이벤트 로그는 추가 전용이라 되돌릴 수 없다), 상품 축에서는 사장님이 아직 들고 있는 다른 기기와 그 상품에 딸린 그룹 기록이 서로 다른 해시를 보게 되기 때문이다.

## 남은 한계

**등록 슬롯 선점.** 전화번호가 위조 가능한 값이라, 공격자가 피해자 번호로 등록 상한(8)을 채워 그 번호의 사전등록을 막을 수 있다. 주문을 가져가지는 못하지만 복구 기능 자체를 표적 무력화한다. 전화번호 본인확인(문자 인증) 없이는 구조적으로 닫히지 않는다. 등록에는 실제 소유 증명이 필요하므로 공격자도 그 번호로 주문을 8건 넣어야 한다는 비용은 있다. 2026-09-20·22 카톡으로 고객에게 알렸고, 문자 인증 도입 여부는 고객 결정으로 남아 있다. 자가 복구 화면은 이 한계를 안고 연다.

## 복구 코드 노출 (2026-09-22)

고객이 "복구 코드를 어디서 확인하나요"라고 물었다. 코드는 내 주문 → 접힌 "이전 주문이 보이지 않나요?" → "복구 코드 보기" 두 번 아래에 있었고, 빈 목록 화면에는 아무 단서가 없었다.

키 분실 경고(`lostKey`)는 로컬 주문 캐시가 남아 있을 때만 켜지는데, 모바일이 사이트 저장소를 통째로 비우면 캐시도 같이 사라져 정확히 이 경우에 경고가 뜨지 않았다. 조회가 끝났는데 목록이 비어 있으면 안내를 펼치고 복구 코드를 바로 계산해 보여주도록 바꿨다(`b9e832f`). 복구 코드는 공개 식별자라 자동 노출해도 권한이 넘어가지 않는다.
