# 주문 조회 권한 복구 기능

## 배경

주문·상품·그룹의 조회 권한은 브라우저에 보관된 권한 키의 해시로만 판정한다. 전화번호와 visitorId 는 사장님·그룹 화면에 노출되는 값이라 증명으로 인정하지 않는다(`filterCustomerOrdersForProof_` 주석).

모바일 브라우저가 사이트 저장소를 비우면 세 키가 한꺼번에 사라지고, 그 사용자는 내 주문 0건·사장님 관리 0건·그룹 채팅 불가 상태가 된다. 2026-09-17~09-20 고객 보고의 "하루만 지나면 0으로 뜬다"가 이 현상이다.

## 설계 원칙

**전화번호는 조회 범위이지 권한 근거가 아니다.** `publishCustomerOrder_`는 `order.customerPhone`을 클라이언트 값 그대로 받아 길이만 검사한다. 전화번호를 근거로 권한을 주면 남의 번호로 주문 한 건을 만든 뒤 그 번호의 모든 주문과 취소 권한까지 인수할 수 있다.

**시트 행을 다시 쓰지 않는다.** 같은 주문에 소유 해시가 둘이면 `filterCustomerOrdersForProof_`가 충돌로 판정해 원래 주인에게까지 숨긴다. 소유 해시는 주문 내역과 이벤트 로그 스냅샷 양쪽에 있고 스냅샷은 상태 전이마다 누적되므로, 재작성 방식은 부분 실패가 곧 영구 은닉이 된다. 대신 **승계만 기록하고 읽는 시점에 해석한다.**

**확인번호 원문은 Apps Script 에 도달하지 않는다.** scrypt 파생·비교는 Vercel 에서만 한다.

## 구현 상태

| 경로 | 상태 |
| --- | --- |
| 승계 저장소·해석 (주문·그룹·상품 축) | 완료 |
| 쓰기 경로 승계 (게시·취소) | 완료 |
| 등록·복구 처리, 레이트리밋 | 완료 (콜렉터) |
| **관리자 재연결** | **완료·배포** |
| 고객 자가 등록·복구 (API·화면) | 미완 |

관리자 재연결은 **이미 키를 잃은 기록**을 되살린다. 사전등록 방식은 키가 살아있을 때 결박해 둔 것만 되살리므로, 이미 잃은 사용자에게는 쓸 수 없다.

## 관리자 재연결 사용법

1. 사용자가 자기 기기의 사용자 앱에서 **복구 코드**를 확인한다. 이 값은 권한 해시(공개 식별자)이며 원본 토큰이 아니다.
2. 관리자가 **대면·유선으로 본인을 확인**한다. 이 전제는 두 화면에 명시되어 있다.
3. 관리자 앱 → 상품·주문 관리 → 해당 상품 → 재연결할 주문 선택 → 복구 코드 입력 → 사유 입력 → 실행.

제약:
- 한 번에 최대 50건, 소유 키가 서로 다르거나 없는 주문은 함께 묶지 않는다.
- 한 기기에 두 번째 승계를 기록해 기존 승계를 무효로 만들 수 없다.
- 권한보다 이력을 먼저 남긴다. 이력 기록이 실패하면 권한도 생기지 않는다.

## 작업 중 발견해 수정한 기존 결함

- `rate_begin`이 호출 버킷과 무관하게 **관리자 PIN 검증자를 응답에 싣고 있었다.** 복구가 같은 리미터를 재사용하면 관리자 자격증명이 복구 응답으로 새어 나간다. 관리자 버킷일 때만 싣도록 막았다.
- 주문 확인 키를 저장하는 곳만 저장공간 부족 복구가 빠져 있어, 저장이 실패하면 다음 접속에 새 키가 만들어지고 이전 주문 전체가 조회 대상에서 빠졌다.

## 남은 한계

**등록 슬롯 선점.** 전화번호가 위조 가능한 값이라, 공격자가 피해자 번호로 등록 상한을 채워 그 번호의 사전등록을 막을 수 있다. 주문을 가져가지는 못하지만 복구 기능 자체를 표적 무력화한다. 전화번호 본인확인(문자 인증) 없이는 구조적으로 닫히지 않는다. 고객 자가 복구를 열기 전에 결정이 필요하다.
