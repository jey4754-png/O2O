## 역할별 확인

1. **사용자:** 본래 브라우저·프로필로 참여 내역을 확인한다. 입금 요청 후 그룹 채팅의 상태와 내 주문 상태가 함께 바뀌는지 확인한다. 실제 송금 확인은 운영자의 업무이며 앱 버튼만으로 금융기관 입금을 검증하지 않는다.
2. **호스트·관리자:** 입금확인요청을 실제 확인한 뒤 입금완료로 변경한다. 그룹 상태는 모집 중 → 모집 완료 → 상품 구매 완료 → 전달 완료이며 허용된 한 단계 되돌리기를 제공한다. 변경 이력이 남는지 확인한다.
3. **사장님:** 같은 전화번호만으로 다른 브라우저의 관리 권한이 생기지는 않는다. 원래 상품을 등록한 브라우저·프로필과 관리키를 유지한다. 중앙 조회 실패 안내는 상품이 0개라는 뜻이 아니다.
4. **상품 관리자:** 검색 후 정확한 상품과 주문을 선택한다. 삭제·취소·이미지 변경에는 사유를 입력한다. 실패한 경우 메시지와 선택을 확인하고 재시도한다. 다른 상품까지 성공했다고 추정하지 않는다.

## 오류 접수와 처리 완료 기준

- 이미 받은 상품·그룹 링크를 사건 기록에 유지한다. 새로운 오류에는 발생 시각, 역할, 브라우저, 눌렀던 버튼, 화면 메시지를 덧붙인다. PIN·관리키·개인정보를 일반 채팅이나 오류 로그에 보내지 않는다.
- 로컬 화면에 카드가 존재하는 것, 중앙에 저장된 것, 다른 화면으로 상태가 반영된 것을 따로 확인한다.
- 고객 데이터의 상태를 시험 삼아 변경하지 않는다. 실패·응답 지연·중복 클릭·재시도·새로고침·다른 역할 전환은 테스트 저장소에서 재현한다.
- 수정 코드는 `pnpm verify:release`로 검사하고, 운영에 연결한 배포 ID·자산 해시·읽기 결과를 기록한다. 좁은 후속 수정은 영향받는 회귀 검수와 빌드를 추가한다. 통과하지 못한 검사나 하지 않은 실기기 검수를 완료로 표시하지 않는다.
- 고객 제보의 종료에는 정확한 재현 사례와 중앙 저장·반영 확인이 필요하다. 복구에 원래 브라우저의 원본이 필요하면 기능 수정과 별도 미완료 항목으로 유지한다.

## 원본 보존과 복구

브라우저 저장소 삭제, 상품 삭제 후 재등록, 게시 버전 초기화, 전화번호만으로 소유권 연결은 복구 절차가 아니다. 먼저 원래 브라우저·프로필을 보존하고 정확한 원본과 관리 권한을 확인한다. 확인되지 않은 주문·입금 상태를 새로 만들지 않는다.

서버 자료를 변경할 때는 해당 시트와 Apps Script 속성을 비공개로 백업하고 복구 범위를 정한다. 코드 백업만으로 운영 데이터 백업이 완료된 것은 아니다. 백업의 비밀값은 공개 저장소·메일·일반 채팅에 첨부하지 않는다. 현재 시트를 이전 자료로 통째로 덮어쓰면 그 뒤의 주문과 이력이 유실될 수 있다.
